# 测试面试训练（2026-08-03 开始）

> 形式：模拟面试 → 出题 → 作答/学答案 → 记录 → 换场景巩固

## 第一轮 — 测试基础（4 题，直接学答案）

### ① 测试的目的是什么？

**答法骨架**：尽早发现缺陷 + 验证是否符合需求 + 降低风险/发布成本；**不能保证无 Bug**——测试是抽样，只能降低风险不能消除。

**坑**：只答"找 Bug"太单薄，要带"验证需求"和"风险评估"两个维度。

### ② 黑盒 vs 白盒

**一句话**：黑盒看表现、白盒看结构、灰盒看接口。

- 黑盒：不管实现，从用户/需求角度验证输入→输出，方法有等价类/边界值/场景法，功能测试都是黑盒
- 白盒：看代码逻辑（语句/分支/条件覆盖），开发做单元测试时用
- 灰盒：了解部分结构，如接口测试——知道数据结构但不管实现

**坑**：只背定义不举方法例子 → 要补"等价类/边界值→黑盒，分支覆盖→白盒"。

### ③ 注册页面等价类 + 边界值（用户名 6~16 位字母数字；密码 ≥8 位含数字和字母）

```
用户名：
  有效：10 位字母数字 → 成功
  无效：含特殊字符（abc@123）→ 提示仅字母数字
  无效：3 位 → 提示长度不够
  边界：6 → 成功；5 → 报错；16 → 成功；17 → 报错
密码：
  有效：abc12345 → 成功
  无效：纯数字 → 提示需含字母
  无效：纯字母 → 提示需含数字
  边界：8 → 成功；7 → 报错
```

**坑**：
- 无效类要拆多个（短/特殊字符/缺字母/缺数字是不同类），不能只分"合法/不合法"
- 边界值取 4 个点：min、min-1、max、max+1
- 一个用例只测一个边界，用户名边界和密码边界分开测

### ④ 测试用例要素 + 为什么预期结果必须

**要素**：编号、标题、前置条件、测试步骤、测试数据、预期结果（+优先级/模块/实际结果）。

**预期结果为什么必须有**：没有它就无法判定通过/失败，测试失去意义。且必须**具体可验证**——写"页面提示'注册成功'并跳转登录页"，不写"页面正常"。

**坑**：前置条件不能写"正确的信息"（主观词），要写具体规则——错题本已记过这条。

## 第二轮 — 场景题（自己作答后被纠错）

### ① 登录功能怎么测（我的回答：只说了错误/正确账号密码 5 个点 → ⭐⭐）

**教训**：面试要求 15+ 条，按五维度展开：

```
功能/校验：正确/错误密码、错误账号、账号不存在、账号锁定/禁用/注销、空值、超长特殊字符
安全：SQL注入（1' OR '1'='1）、XSS（<script>alert(1)</script>）、输错N次锁定/验证码、HTTPS加密
交互：密码显示切换、记住密码、忘记密码、回车登录、刷新后登录态
会话：token生成/失效/登出、同一账号多地登录
兼容性能：多浏览器、弱网、大量并发登录
```

**关键细节**：账号不存在不能提示"账号不存在"（泄露账号信息），要统一提示"账号或密码错误"。

### ② Bug 生命周期（我的回答：提交→开发解决→回归 → ⭐⭐）

**完整状态链**：

```
New → Assigned → Fixed → Verified → Closed
         ↑           ↑
      Rejected（驳回）Reopen（验证不通过打回）
```

**教训**：漏了 Assigned / Rejected / Verified / Reopen 四个状态；"开发修完必须测试验证通过才能 Close"——这是测试的话语权。

### ③ Severity vs Priority（决策对，概念没说出 → ⭐⭐⭐）

| | Severity 严重级 | Priority 优先级 |
|--|----------------|----------------|
| 含义 | 破坏程度（技术角度） | 修复紧急程度（业务角度） |

**不一致的经典例子**：
- 支付按钮失效 → 双高 → 先修
- Logo 颜色错 + 大客户发布会指定页面 → Severity 低 Priority 高 → 也得先修
- 没人用的报表数据全错 → Severity 高 Priority 低 → 下版本修

**我的坑**：只答"修复支付按钮"是决策题，面试官要的是"说得出概念 + 举例不一致场景"。

## 第三轮 — 巩固 + 迁移（部分通过）

### ① Bug 生命周期中文版（要求记中文名）

```
新建 → 已分配 → 已修复 → 已验证 → 已关闭
  ↑          ↑
 已驳回 ←   重新打开（验证不通过打回去）
```

**口诀：新建分配修复验证关，中途驳回重新开。**（下次口头考）

### ② 购物车怎么测（我的回答：只说了角标 2 点 → ⭐）

**教训：测试先主流程后细节。**角标是 UI 细节，核心是：
- 加购（未登录/已登录）→ 删除 → 改数量 → **价格计算** → 结算跳转
- 数量 0/负数/超库存、商品下架、库存不足
- 优惠券/满减叠加
- 未登录加购登录后还在？PC/App 多端同步
- 并发：抢购超卖、加购和下单同时进行

### ③ Severity ≠ Priority 教科书案例（结论对理由错 → ⭐⭐⭐）

**Bug A 重复邮件**：下单成功只多发邮件 → **Severity 中**，但影响所有用户+信任风险 → **Priority 高** → 先修
**Bug B 导出按钮无反应**：功能完全不可用 → **Severity 高**，但下月才上线没人用 → **Priority 低** → 下版本修

**我的坑**：说"A 是主流程错误"——错，主流程（下单）没坏。**答这类题套路：先判 Severity（坏得多狠）→ 再判 Priority（多急着修）→ 最后说结论 + 说一句"这正好体现严重级和优先级不一致"。**

## 第四轮 — 巩固局（部分通过）

### ① Bug 生命周期（⭐⭐⭐⭐ 基本过关）

主链路 5 个全对：新建→分配→修复→验证→关闭 ✅
- 坑："打回"不是标准术语，是**驳回**（开发拒绝：不是Bug/重复/无法复现）
- **重新打开**要说清场景：验证**不通过** → 打回重开，回到分配

### ② 搜索功能（⭐⭐⭐ 漏了安全维度）

搜索框 = 注入/XSS 重灾区，必须套"输入框三件套"：
- **凡是输入框 → 校验 + SQL注入（1' OR '1'='1）+ XSS（<script>alert(1)</script>）必测**
- 登录、搜索、注册、下单通用
- 补：空搜索、超长、前后空格、回车触发、搜索历史、联想、翻页排序、结果统计

### ③ Priority 判断方法（不会判优先级 → ⭐⭐⭐）

**三问口诀：① 影响多少人？② 碰没碰钱和数据？③ 是不是现在就要用？**

**测试铁律：凡是跟钱相关的错误 → Severity 直接判高（Critical），Priority 直接判高。**
- 金额计算错误 = 财务损失 + 信任崩塌，仅次于系统崩溃
- Bug C 错别字：能点没人受影响 → 双低，下版本修
- Bug D 金额多 10 元：所有用户+钱 → 双高，立刻修

### ④ 黑盒 vs 白盒（跳题了 ⚠️）

**面试跳题是大忌，半对也比沉默强。**
一句话：黑盒看表现，白盒看结构。
