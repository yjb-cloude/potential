## 一、测试理论基础

### 软件质量模型

**ISO/IEC 25010** 是业界通用的软件质量模型，定义了以下八大质量特性：

| 质量特性 | 说明 | 典型测试关注点 |
|---------|------|--------------|
| 功能性 (Functional Suitability) | 功能正确、完整、恰当 | 功能测试、边界验证 |
| 性能效率 (Performance Efficiency) | 时间行为、资源利用率 | 负载测试、压力测试 |
| 兼容性 (Compatibility) | 共存、互操作 | 跨浏览器、跨版本测试 |
| 易用性 (Usability) | 可识别、可学习、可操作 | 用户体验测试、A11y |
| 可靠性 (Reliability) | 成熟度、可用性、容错 | 稳定性测试、故障恢复 |
| 安全性 (Security) | 机密性、完整性、抗抵赖 | 渗透测试、SQL 注入 |
| 维护性 (Maintainability) | 模块化、可复用、可分析 | 代码审查、静态分析 |
| 可移植性 (Portability) | 适应性、可部署 | 环境兼容测试 |

**面试重点**：至少能说出 5 个质量特性及其测试含义，面试时用"我们项目主要关注功能、性能和安全"来引出实际经验。

### 测试类型

- **功能测试** — 验证功能是否符合需求，是测试工作的主体
- **性能测试** — 验证响应时间、吞吐量、资源使用（详见 [[performance-testing]]）
- **安全测试** — 发现系统安全漏洞（XSS、CSRF、SQL 注入、越权）
- **兼容性测试** — 不同浏览器/OS/设备/分辨率下正常工作
- **易用性测试** — 用户操作是否直观、高效，符合使用习惯
- **可靠性测试** — 系统在长时间/高负载下是否稳定，异常恢复能力
- **回归测试** — 修改后验证原有功能不受影响，自动化最擅长的场景
- **冒烟测试** — 构建后对核心功能快速验证，决定是否进入详细测试

**面试重点**：能区分"功能 vs 性能 vs 安全"的核心差异，说明回归测试的重要性。

### 测试级别

```
需求分析 → 单元测试 → 集成测试 → 系统测试 → 验收测试
                              ↓
                          UAT (用户验收)
```

| 级别 | 测试对象 | 测试人 | 典型时间 |
|------|---------|-------|---------|
| 单元测试 (Unit) | 方法/函数/类 | 开发 | 编码阶段 |
| 集成测试 (Integration) | 模块间接口 | 开发/测试 | 模块联调 |
| 系统测试 (System) | 完整系统 | 测试 | SIT 阶段 |
| 验收测试 (UAT) | 业务流程 | 用户/产品 | 上线前 |

**面试重点**：每个级别的定位和负责方，特别是"集成测试和系统测试的区别"是高频题。

### 测试方法

| 维度 | 分类 | 说明 |
|------|------|------|
| 是否关注内部结构 | **白盒** (结构逻辑) / **黑盒** (功能) / **灰盒** (结合) | 面试常问区别 |
| 是否运行代码 | **静态** (评审/走查) / **动态** (执行) | 静态发现 30% 以上的缺陷 |
| 执行方式 | **手工** / **自动化** | 手工做探索，自动化做回归 |
| 测试策略 | 正向 (验证能做) / 逆向 (验证防错) | 异常场景覆盖 |

**面试重点**：白盒 vs 黑盒的区别和适用场景是必考题。

### 测试设计方法

| 方法 | 核心思想 | 适用场景 |
|------|---------|---------|
| **等价类划分** | 将输入域分为有效/无效等价类，每个类取一个代表值 | 所有输入框测试 |
| **边界值分析** | 取边界值（最小值、最大值、略超边界） | 数值范围输入 |
| **因果图法** | 用逻辑图表示输入条件和输出结果的关系 | 组合逻辑复杂的场景 |
| **判定表** | 条件与动作的组合矩阵，覆盖所有逻辑路径 | 业务规则较多（如审批流程）|
| **正交实验法** | 用正交表选择最少的组合覆盖最多因素 | 多参数组合（如筛选条件）|
| **场景法** | 基于业务流程的路径分析 | 端到端业务流程 |
| **错误推测法** | 凭经验推测可能出Bug的地方 | 补充用例，经验依赖强 |

**面试重点**：等价类划分 + 边界值分析是最常考的组合，面试常给一个输入条件让你现场设计用例。场景法在业务测试中应用最广。

### 测试流程

```
需求分析 → 测试计划 → 用例设计 → 用例评审 → 执行测试 → 缺陷管理 → 测试报告
    ↓          ↓           ↓                    ↓             ↓          ↓
 理解需求   评估工期   编写用例             记录结果     跟踪Bug   总结质量
 识别风险   制定策略   评审用例             执行用例     回归验证   给出结论
```

**面试重点**：能完整说出一条测试流程，并能具体描述每个阶段的产出物。

## 二、测试管理

### 测试计划要素

一份完整的测试计划应包含：

1. **测试范围** — 测什么、不测什么（In Scope / Out of Scope）
2. **测试策略** — 各类型测试的方法和工具选择
3. **资源安排** — 人员、环境、数据准备
4. **时间计划** — 各阶段的起止时间、里程碑
5. **准入/准出标准** — 开始测试和结束测试的条件
6. **风险及应对** — 识别风险，制定 mitigation 方案
7. **交付物** — 测试用例、Bug 报告、测试报告等

**面试重点**：提到"准入标准"和"准出标准"会加分，这是区分新手和有经验者的细节。

### 测试用例编写规范

标准的测试用例包含以下要素：

```
标题：简短描述测试场景（【模块】_测试点_条件）
前置条件：测试开始前必须满足的条件
测试步骤：清晰的操作步骤，编号排列
预期结果：具体可验证的结果描述
"""

示例：
标题：【登录】_密码错误_输入错误密码登录
前置：用户已注册，数据库中有该账号
步骤：1. 打开登录页面 2. 输入正确用户名 + 错误密码 3. 点击登录
预期：页面提示"用户名或密码错误"，不会跳转
```

**优秀用例的特征**：
- **原子性**：一个用例只测一个点
- **可复现**：严格按照步骤执行一定能复现
- **可判定**：预期结果明确，任何测试人员执行结果一致
- **独立性**：用例之间不互相依赖

**面试重点**：面试官可能会给你一个功能，让你现场口述测试用例设计思路。

### Bug 生命周期

```
New (新提交)
  │
  ▼
Assigned (已分配) ←─── Rejected (驳回：非Bug/重复/无法复现)
  │
  ▼
Fixed (已修复)
  │
  ▼
Verified (已验证)
  │
  ▼
Closed (已关闭)
  │
  └───→ Reopen (重新打开：验证不通过)
```

**关键的流转规则**：
- 开发 Fix 后必须指定给测试验证，不能直接 Close
- 测试验证不通过则 Reopen，回到 Assigned
- Rejected 需要有充分理由，测试有异议可以提出来讨论

**面试重点**：Bug 生命周期流程几乎必问，要能用流程图口述清楚。

### Bug 严重级别 vs 优先级

| 级别 | 严重程度 (Severity) | 优先级 (Priority) |
|------|-------------------|-------------------|
| P0/Critical | 系统崩溃/主功能不可用 | 立即修复，阻塞发布 |
| P1/Major | 功能无法正常使用 | 本版本必须修复 |
| P2/Minor | 功能可用但体验不佳 | 本版本应修复 |
| P3/Trivial | 界面问题/文字错误 | 可以延期/下一版本 |

**核心区别**：
- **Severity**：Bug 对系统的破坏程度（技术角度）
- **Priority**：Bug 被修复的紧急程度（业务角度）
- 高 Severity 不一定高 Priority（如"主页Logo显示错位" Severity 低但如果是大客户要求则 Priority 高）
- 低 Severity 不一定低 Priority（如"用户名需要加特殊字符校验"虽小但必须改）

**面试重点**：能举例说明 Severity 和 Priority 的四种组合情况是加分项。

### 测试报告模板

```
XX 项目 V1.0 功能测试报告

1. 测试概述：测试范围、时间、人员
2. 测试环境：硬件配置、软件版本、浏览器
3. 测试统计：总用例数、通过/失败/阻塞数、通过率
4. 缺陷统计：Bug 总数、按严重级别分布、按模块分布
5. 遗留问题：已知但未修复的 Bug 及影响评估
6. 测试结论：是否达到上线标准，建议是否发布
7. 风险提示：已知风险和未来建议
```

**面试重点**：提到"遗留问题分析"和"上线建议"能体现质量意识。

### 测试度量指标

| 指标 | 公式 | 含义 |
|------|------|------|
| **用例通过率** | 通过用例数 / 总执行用例数 | 反映当前版本质量 |
| **缺陷密度** | Bug 数 / 代码行数(或功能点数) | 每千行代码 Bug 数，评估模块质量 |
| **用例覆盖率** | 已覆盖需求数 / 总需求数 | 功能点覆盖率，衡量充分性 |
| **自动化覆盖率** | 自动化用例数 / 总用例数 | 标记回归效率 |
| **缺陷发现率** | 测试发现的 Bug / (测试发现 + 线上发现) | 测试质量评估 |
| **需求稳定性** | 需求变更次数 | 影响测试计划和用例设计 |

**面试重点**："用例通过率"和"缺陷密度"是最常用的两个指标。面试官会问"你们团队用什么指标衡量质量"。

## 三、自动化测试

### 测试金字塔与框架类型

详见 → [[test-automation-types]]

核心要点记忆：

```
         /\
        /  \         UI 自动化（慢、贵、维护成本高）
       /    \
      /------\
     /        \       API 自动化（性价比最高）
    /          \
   /------------\
  /              \    单元测试（快、便宜、覆盖面广）
/------------------\
```

- **单元测试**占比 60-70%，**API 测试**占比 20-30%，**UI 测试**占比 5-10%
- API 自动化是性价比最高的分层，投入产出比最优
- 框架类型：线型 → 模块化 → 数据驱动 → 关键字驱动 → 混合框架

### [[selenium-webdriver]]

- **元素定位**：ID > Name > CSS Selector > XPath（按优先级选择）
  - CSS: 速度快、语法简洁
  - XPath: 能定位复杂结构，但性能稍差
- **等待机制**：
  - Implicit Wait — 全局等待，找元素前等 N 秒
  - Explicit Wait — 等待特定条件满足（最推荐）
  - Fluent Wait — 带 polling interval + ignore exceptions
- **Page Object 模式** — 每个页面一个类，封装元素和操作，测试只写流程
- **多浏览器** — WebDriver 接口 + ChromeDriver / FirefoxDriver / EdgeDriver + RemotesDriver (Grid)
- **常用操作**：click / sendKeys / getText / select 下拉框 / Alert / Window 切换 / Frame 切换

**面试重点**：
- Page Object 设计模式几乎是必问
- 等待机制的选择理由（为什么不用 Thread.sleep）
- 如何处理弹窗、新窗口、iframe

### [[rest-assured-api]]

- **核心风格**：Given-When-Then 三段式链式调用

```java
given()
    .header("Authorization", "Bearer xxx")
    .body(requestBody)
.when()
    .post("/api/users")
.then()
    .statusCode(201)
    .body("data.name", equalTo("Alice"));
```

- **JSON Schema 校验**：用 `matchesJsonSchemaInClasspath("schema.json")` 校验响应结构
- **认证处理**：Basic Auth / OAuth2.0 / Token 动态获取
- **参数传递**：提取上一个接口的响应值传给下一个接口（Extract + 变量保存）

### [[junit-testng]]

| 特性 | JUnit 5 | TestNG |
|------|---------|--------|
| 核心注解 | @Test, @BeforeEach, @AfterEach | @Test, @BeforeMethod, @AfterMethod |
| 参数化 | @ParameterizedTest + @CsvSource | @DataProvider |
| 分组 | @Tag | @Test(groups = "...") |
| 依赖测试 | @Order | dependsOnMethods / dependsOnGroups |
| 监听器 | Extensions API | ITestListener / IAnnotationTransformer |

**面试重点**：
- @BeforeClass / @BeforeMethod 的执行顺序
- 数据驱动测试（JUnit5 @CsvSource / @MethodSource vs TestNG @DataProvider）
- 断言库：AssertJ / Hamcrest 的流式断言优于原生 Assert

### [[auto-framework-design]]

企业级自动化框架的核心组成：

1. **驱动管理 (Driver Management)** — WebDriver 统一初始化、复用、销毁，支持多浏览器 + Remote
2. **配置化 (Configuration)** — 环境/浏览器/超时等参数统一在 config 文件中管理 (YAML/Properties)
3. **数据驱动 (Data-Driven)** — Excel / YAML / JSON / CSV 读取测试数据，与用例逻辑分离
4. **重试机制 (Retry)** — 用例失败自动重试 N 次（TestNG IRetryAnalyzer / JUnit5 自定义 Extension）
5. **报告集成 (Reporting)** — Allure / ExtentReports / ReportNG 定制测试报告
6. **日志系统 (Logging)** — Log4j / SLF4J 记录执行过程
7. **持续集成 (CI/CD)** — Jenkins / GitHub Actions / GitLab CI 集成自动化执行
8. **失败截图** — 用例失败时自动截图并附加到报告

**面试重点**：
- "你搭建过框架吗？讲一下框架的核心组成部分" — 这是自动化岗位的高频面试题
- 能说出"为什么选择数据驱动"、"如何处理用例依赖"、"如何在 CI 中集成"

## 四、[[api-testing-basics]]

### HTTP 协议基础

- **请求方法**：GET（查）/ POST（增）/ PUT（全量更新）/ PATCH（部分更新）/ DELETE（删）
- **状态码分类**：
  - 2xx：成功（200 OK、201 Created、204 No Content）
  - 3xx：重定向（301 永久、302 临时、304 未修改）
  - 4xx：客户端错误（400 参数错、401 未认证、403 未授权、404 不存在、405 方法不允许）
  - 5xx：服务端错误（500 内部错误、502 网关超时、503 服务不可用）
- **RESTful 规范**：资源 URL 设计、无状态、使用标准 HTTP 方法
- **鉴权方式**：Basic Auth / Bearer Token / JWT / OAuth2.0 / API Key

### 接口测试关注点

| 关注维度 | 具体检查项 |
|---------|-----------|
| 功能正确性 | 返回状态码、响应体字段值、数据操作正确 |
| 幂等性 | GET / DELETE / PUT 多次请求结果一致 |
| 异常处理 | 参数缺失/类型错误/越界、未认证访问、不存在的资源 |
| 性能 | 接口响应时间是否在预期内（P99 < 500ms）|
| 安全 | SQL 注入／越权（水平越权、垂直越权）|

**面试重点**：
- POST 和 PUT 的区别
- 接口测试如何做参数校验（等价类 + 边界值）
- 如何测试幂等性

## 五、[[performance-testing]]

### 核心术语

| 术语 | 含义 | 说明 |
|------|------|------|
| **QPS** | Queries Per Second | 每秒查询数，常用于读接口 |
| **TPS** | Transactions Per Second | 每秒事务数，常用于写接口 |
| **RT** | Response Time | 响应时间（含网络+服务端） |
| **P99** | 99% 的请求响应时间 | 衡量长尾延迟，P99 < 1s 是常见目标 |
| **并发数** | 同时处理的请求数 | 系统能支撑多少在线用户 |
| **吞吐量** | 系统单位时间处理的请求数 | TPS/QPS |

### 性能测试流程

```
基准测试 → 负载测试 → 压力测试 → 稳定性测试
   ↓          ↓           ↓           ↓
单用户基线  逐步加压   极限施压   长时间运行
```

1. **基准测试 (Baseline)** — 单用户场景，确定性能基线
2. **负载测试 (Load)** — 模拟预期用户数，验证是否达标
3. **压力测试 (Stress)** — 不断加压直到系统崩溃，找到瓶颈
4. **稳定性测试 (Soak)** — 长期运行（如 24h）检测内存泄漏

### JMeter 核心组件

- **线程组 (Thread Group)** — 模拟用户数、Ramp-Up 时间、循环次数
- **Sampler** — HTTP Request / JDBC Request / Debug Sampler
- **断言 (Assertion)** — Response Assertion / Duration Assertion / JSON Assertion
- **监听器 (Listener)** — 查看结果树 / 聚合报告 / 图形结果
- **前置/后置处理器** — 参数提取（JSON Extractor / Regular Expression Extractor）
- **配置元件** — CSV Data Set Config / HTTP Cookie Manager / HTTP Header Manager

### 性能瓶颈定位

```
用户端 → 网络 → 负载均衡 → 应用服务器 → 中间件 → 数据库
                                                    ↓
                                               慢查询/连接池
```

| 层次 | 常见瓶颈 | 排查工具 |
|------|---------|---------|
| 前端 | 资源过大、请求过多 | Chrome DevTools / Lighthouse |
| 网络 | 带宽、DNS 解析 | Wireshark / ping / traceroute |
| 应用 | 慢代码、线程阻塞 | JProfiler / Arthas / YourKit |
| 数据库 | 慢 SQL、索引缺失、连接池满 | MySQL slow log / EXPLAIN / DBA |
| 缓存 | 缓存穿透、击穿、雪崩 | Redis-cli / Grafana |
| 中间件 | 队列积压 | Kafka lag / RabbitMQ 管理台 |

**面试重点**：
- QPS / TPS / RT / P99 的定义和区别
- 能说出"性能测试的完整流程"
- "项目中有没有遇到过性能问题？你们怎么定位的？"

## 六、安全测试

> 来源：路线图第五阶段（安全测试）
> 安全测试是测试工程师的进阶技能，面试中作为差异化亮点展示。

### 安全测试基础

**核心概念**：
- **安全测试目的**：发现系统安全漏洞，确保数据的机密性、完整性和可用性
- **安全测试 vs 功能测试**：功能测试验证"能否工作"，安全测试验证"能否被攻击"
- **OWASP Top 10**：Web 应用最危险的 10 大安全风险，每 3-4 年更新一次

**OWASP Top 10（2021）核心条目**：

| 排名 | 漏洞类型 | 简要说明 |
|------|---------|---------|
| A01 | **失效的访问控制 (Broken Access Control)** | 越权操作（普通用户访问管理员功能） |
| A02 | **加密机制失效** | 敏感数据明文传输/存储 |
| A03 | **注入 (Injection)** | SQL、NoSQL、OS 命令注入 |
| A04 | **不安全的设计** | 缺少安全设计导致的漏洞 |
| A05 | **安全配置错误** | 默认密码、目录列表、错误信息泄露 |
| A06 | **易受攻击和过时的组件** | 使用有已知漏洞的第三方库 |
| A07 | **身份认证失效** | 弱密码、暴力破解、Session 固定攻击 |
| A08 | **软件和数据完整性故障** | CI/CD 流水线安全、自动更新机制 |
| A09 | **安全日志和监控不足** | 无法检测和响应安全事件 |
| A10 | **服务端请求伪造 (SSRF)** | 服务器伪造请求访问内部系统 |

### 常见安全漏洞测试

#### SQL 注入

**原理**：用户输入被拼接到 SQL 语句中执行，导致数据库被非法操作。

```sql
-- 假设登录 SQL
SELECT * FROM users WHERE username = 'admin' AND password = 'xxx'

-- 攻击者输入用户名: admin' -- 
-- SQL 变成:
SELECT * FROM users WHERE username = 'admin' -- ' AND password = 'xxx'
-- 注释符号 -- 后面的条件被去掉，成功绕过密码验证

-- 更危险的攻击: admin' OR '1'='1
SELECT * FROM users WHERE username = 'admin' OR '1'='1' AND password = 'xxx'
-- OR '1'='1' 恒为真，返回所有用户
```

**测试要点**：
- 所有输入框尝试 `'` `"` `--` `#` `OR '1'='1'` `OR 1=1--`
- URL 参数注入测试
- 请求头注入测试（User-Agent、Cookie）
- 检查数据库错误信息是否泄露给用户
- 验证是否使用 PreparedStatement / 参数化查询

#### XSS（跨站脚本攻击）

**原理**：攻击者将恶意脚本注入网页，在用户浏览器中执行。

| 类型 | 说明 | 测试方法 |
|------|------|---------|
| **反射型 XSS** | 恶意脚本在 URL 中，服务端返回时未转义 | 在搜索框/URL 参数中输入 `<script>alert(1)</script>` |
| **存储型 XSS** | 脚本存储在服务器（如评论区），其他用户访问时触发 | 在评论区/用户资料中输入 `<img src=x onerror=alert(1)>` |
| **DOM 型 XSS** | 客户端 JS 代码中，未对用户输入做安全处理 | 分析前端 JS 代码中从 URL/hash 取值并写入页面的操作 |

**测试要点**：
- 所有输入点测试 `<script>alert(1)</script>` 
- 测试 HTML 标签注入：`<img src=x onerror=alert(1)>` `<a href="javascript:alert(1)">`
- 测试 URL 编码绕过：`%3Cscript%3Ealert(1)%3C/script%3E`
- 验证输出编码（HTML Entity 编码、JS 编码、URL 编码）

#### CSRF（跨站请求伪造）

**原理**：用户在已登录状态下，点击恶意链接，在不知情的情况下执行了非本意的操作。

**测试要点**：
- 检查敏感操作（修改密码、转账、删除）是否有 CSRF Token
- 检查 Referer/Origin 头校验
- 验证 Token 是否与用户 Session 绑定、是否可预测、是否每次变化
- 尝试不带 Token 或带错误的 Token 发起请求

**防御机制**：
- CSRF Token（服务端生成，请求时校验）
- SameSite Cookie 属性（Strict / Lax / None）
- 关键操作二次验证（输入密码、短信验证码）

#### 越权测试

| 类型 | 说明 | 测试方法 |
|------|------|---------|
| **水平越权** | 用户 A 访问用户 B 的同级别资源 | 修改 URL 中的 ID、他人的订单号 |
| **垂直越权** | 普通用户访问管理员功能 | 普通用户 Token 尝试访问 /admin 接口 |

**测试要点**：
- 修改 URL 参数中的用户 ID/订单号，尝试访问他人数据
- 低权限用户直接访问高权限 API 端点
- HTTP 方法越权：DELETE /api/users/1（普通用户能否删除）
- 批量赋值：修改请求中的 role=admin 字段

### 安全测试工具

| 工具 | 用途 | 掌握程度 |
|------|------|---------|
| **Burp Suite** | 抓包、重放、扫描、暴力破解（代理工具） | 核心掌握 |
| **SQLMap** | 自动化 SQL 注入检测与利用 | 了解使用 |
| **Nmap** | 端口扫描、服务发现 | 了解 |
| **AWVS / AppScan** | 自动化安全扫描（商业） | 了解 |
| **ZAP** (OWASP) | 开源安全扫描器 | 了解 |

### Burp Suite 核心功能

```
Proxy（代理） → 拦截/修改 HTTP 请求
  ↓
Repeater（重放） → 手动修改并重放请求
  ↓
Intruder（暴力破解） → 自动化参数枚举/爆破
  ↓
Scanner（扫描） → 自动发现安全漏洞（专业版）
  ↓
Decoder（编解码） → URL/Base64/Hex 编码解码
```

### 面试重点

1. **"你做过安全测试吗？"**
   - 回答策略：即使没有正式做过，也要说"我在功能测试中会特别关注安全方面"，然后举例 SQL 注入、XSS 测试经验

2. **"登录功能从安全角度怎么测？"**

3. **"什么是 CSRF？怎么测？"**
   - 理解 CSRF 攻击流程
   - 验证 CSRF Token 机制
   - 测试不带 Token 或 Token 错误时的响应

4. **"安全测试和功能测试的关系"**
   - 安全测试是功能测试的补充和延伸
   - 两者都应在测试计划中覆盖
   - 安全测试需要更深的技术理解

### APP 测试 vs Web 测试

| 维度 | Web 测试 | APP 测试 |
|------|---------|---------|
| 运行环境 | 浏览器 | 操作系统（Android/iOS） |

### APP 专项测试

#### 安装/卸载/升级测试

- **安装**：首次安装、覆盖安装、不同渠道安装、存储空间不足时安装
- **卸载**：正常卸载、卸载后数据是否完全清除
- **升级**：新版本覆盖旧版本、跨版本升级、升级后数据是否保留
- **降级**：高版本覆盖低版本是否允许

#### 中断测试

```
来电 → App 是否正常挂起和恢复
短信 → 不影响当前操作
锁屏/解锁 → 回到 App 后状态是否保留
网络切换 → WiFi ↔ 移动数据
低电量 → 性能是否受影响
通知栏 → 下拉通知后 App 状态
Home 键 → 切到后台再切回
```

#### 弱网测试

- **场景**：2G/3G/4G/5G/WiFi 切换、丢包、高延迟
- **工具**：Charles 的 Throttle 功能、Network Link Conditioner
- **关注点**：超时提示、重试机制、数据一致性、消息不重复

#### 兼容性测试

- **多机型**：主流品牌（华为/小米/OPPO/vivo/苹果）、不同屏幕尺寸
- **系统版本**：Android 各版本 API Level、iOS 版本
- **分辨率**：全面屏、刘海屏、折叠屏适配
- **云测平台**：Testin、百度 MTC、 Firebase Test Lab

## 八、Docker 与 CI/CD

> 来源：路线图第三阶段（自动化） + 第六阶段（测试进阶）

### Docker 基础（测试环境管理）

**为什么测试人员需要 Docker**：
- 一键搭建测试环境（数据库、中间件、被测应用）
- 环境一致性（开发/测试/生产使用相同镜像）
- 快速重置测试数据
- 支持 Selenium Grid 分布式测试

**常用命令**：

```bash
# 镜像管理
docker pull mysql:8.0          # 拉取 MySQL 镜像
docker images                   # 查看本地镜像
docker rmi <image_id>           # 删除镜像

# 容器管理
docker run -d -p 3306:3306 --name mysql-test -e MYSQL_ROOT_PASSWORD=123 mysql:8.0
docker ps                       # 查看运行中的容器
docker stop <container_id>      # 停止容器
docker start <container_id>     # 启动容器
docker rm <container_id>        # 删除容器

# 日志与进入容器
docker logs <container_id>      # 查看日志
docker exec -it <container_id> bash  # 进入容器

# Docker Compose（多容器编排）
docker-compose up -d            # 启动所有服务
docker-compose down             # 停止所有服务
```

**Docker Compose 示例（测试环境）**：

```yaml
version: '3'
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: test123
    ports:
      - "3306:3306"
  redis:
    image: redis:7
    ports:
      - "6379:6379"
  app:
    build: .
    ports:
      - "8080:8080"
    depends_on:
      - mysql
      - redis
```

**Docker 在测试中的典型场景**：
- **数据库隔离**：每个测试任务使用独立的 MySQL/Redis 容器
- **Selenium Grid**：用 Docker 启动多个浏览器节点并发执行
- **被测服务**：用 Docker 部署被测应用的指定版本
- **CI 集成**：在 Jenkins/GitHub Actions 中用 Docker 构建和测试

### CI/CD 持续集成

**CI/CD 流程**：

```
代码提交 → 自动构建 → 自动测试 → 自动部署
   ↓          ↓           ↓           ↓
 git push  Maven/Gradle  自动化测试  部署到测试环境
           Spring Boot  单元/接口/UI  或生产环境
```

**Jenkins 核心概念**：

| 概念 | 说明 | 测试中的作用 |
|------|------|-------------|
| **Pipeline** | 流水线任务（Declarative / Scripted） | 定义测试执行流程 |
| **Stage** | 流水线阶段（Build → Test → Deploy） | 划分测试步骤 |
| **Jenkinsfile** | 代码化的流水线定义 | 版本控制测试流水线 |
| **触发器** | 定时 / Git Webhook / 手动触发 | 代码提交自动跑测试 |
| **报告集成** | Allure / JUnit 插件展示测试报告 | 可视化测试结果 |
| **通知** | 邮件 / 钉钉 / 飞书通知 | 失败时及时告警 |

**Jenkins Pipeline 示例**：

```groovy
pipeline {
    agent any
    stages {
        stage('Checkout') { steps { git 'https://github.com/xxx/project' } }
        stage('Build') { steps { sh 'mvn clean compile' } }
        stage('Unit Test') { steps { sh 'mvn test' } }
        stage('API Test') { steps { sh 'mvn test -Papi-test' } }
        stage('UI Test') { steps { sh 'mvn test -Pui-test' } }
        stage('Report') { steps { publishHTML([reportDir: 'target/reports']) } }
    }
    post {
        failure { mail to: 'team@xxx.com', subject: 'Build Failed' }
    }
}
```

**GitHub Actions 示例**：

```yaml
name: Test CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.0
        env: { MYSQL_ROOT_PASSWORD: test }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17' }
      - run: mvn test
      - uses: dorny/test-reporter@v1
        if: always()
        with: { path: 'target/surefire-reports/*.xml' }
```

**CI/CD 面试重点**：
- CI/CD 在测试中的作用（自动化回归、质量门禁）
- Jenkins Pipeline vs GitHub Actions 的异同
- 如何在 CI 中管理测试环境（Docker + 服务容器）
- 失败用例自动重试 + 通知机制
- 测试报告在 CI 中的集成方式

## 九、面试核心攻略

### 高频场景题

**场景 1：登录功能怎么测？**

```
功能类：
  - 正确账号密码能否登录
  - 错误密码提示是否正确
  - 空用户名/密码的校验
  - 密码显示/隐藏切换
  - 记住密码 / 忘记密码流程

安全类：
  - SQL 注入（1' OR '1'='1）
  - XSS（<script>alert(1)</script>）
  - 暴力破解是否有验证码/限制
  - Token 过期是否跳回登录页
  - 登录态下修改密码后旧 Token 是否失效

兼容类：
  - 不同浏览器显示是否正常
  - 手机端响应式适配
  - 输入法兼容（中英文输入）

性能类：
  - 多人同时登录
  - Token 生成时间
```

**场景 2：购物车怎么测？**

```
基础功能：
  - 添加商品/删除商品/修改数量
  - 商品总价计算是否正确
  - 优惠券/满减叠加计算
  - 库存不足时提示

边界/异常：
  - 商品数量为 0、负数、超过库存
  - 商品下架后购物车状态
  - 未登录加入购物车 → 登录后是否还在
  - 多端同步（PC 加了 → App 能看到）

并发：
  - 多人抢购同一商品（超卖问题）
  - 购物车操作和下单同时进行
```

**场景 3：支付流程怎么测？**

```
正向流程：
  - 余额足够时支付成功
  - 余额不足时提示失败
  - 支付成功后订单状态改为已支付
  - 退款流程

异常流程：
  - 支付中网络中断 → 订单状态（等待支付？超时取消？）
  - 重复支付（点了两次支付按钮）
  - 支付超时处理
  - 第三方支付回调失败

安全：
  - 订单金额篡改（拦截请求改金额）
  - 支付结果伪造
  - 重放攻击
```

```
正向流程（全链路）：
  - 下单 → 支付 → 发货 → 确认收货 → 评价
  - 订单状态流转：待支付 → 已支付 → 待发货 → 已发货 → 已收货 → 已完成
  - 订单详情页信息展示（商品、金额、物流、时间）

异常流程：
  - 下单后不支付 → 超时自动取消（30分钟/24小时）
  - 支付后取消订单 → 退款流程
  - 发货后申请退款 → 需要审核
  - 重复下单（同一商品快速点击两次）
  - 库存不足时下单失败

边界场景：
  - 订单号唯一性
  - 订单金额计算（商品价格 × 数量 - 优惠 = 实付）
  - 并发下单（多人同时抢最后一个库存）
```

**场景 5：上传文件怎么测？**

```
功能验证：
  - 支持的文件类型（jpg/png/pdf）能否正常上传
  - 不支持的类型（exe/zip）是否有提示
  - 文件名包含特殊字符（中文、空格、超长文件名）
  - 文件大小边界（刚好等于限制 / 超过 1KB / 超过 10MB）

异常场景：
  - 网络中断时上传 → 是否有重试机制
  - 上传过程中关闭页面 → 文件是否丢失
  - 并发上传多个文件 → 是否有队列或冲突
  - 上传 0KB 空文件
  - 文件内容损坏（修改后缀名伪装）

安全：
  - 文件名注入（../../../etc/passwd）
  - 文件内容检测（伪装 jpg 实际是 exe）
  - 上传恶意文件（病毒、木马）

用户体验：
  - 上传进度条是否显示
  - 大文件上传是否有超时处理
  - 上传成功后预览是否正常
```

**场景 6：表格/列表页怎么测？**

```
分页功能：
  - 总数/每页条数/当前页码显示是否正确
  - 首页/末页/上一页/下一页按钮状态
  - 跳转指定页码（输入 1、输入最大页、输入 0、输入负数、输入超大数）
  - 切换每页条数（10/20/50/100）后数据是否正确

排序功能：
  - 点击表头排序（升序/降序切换）
  - 多字段排序（先按时间排，再按金额排）
  - 排序后分页是否正确（不能出现重复/遗漏）

筛选功能：
  - 单条件筛选（按状态、按时间范围）
  - 多条件组合筛选
  - 筛选后清空条件 → 数据恢复
  - 筛选无结果 → 友好提示

数据展示：
  - 空数据时显示"暂无数据"
  - 大数据量（10万+）页面加载性能
  - 数据对齐、截断、换行显示
```

**场景 7：接口测试怎么测？**

```
参数校验：
  - 必填参数缺失 → 返回 400
  - 参数类型错误（字符串传数字）→ 类型转换或报错
  - 参数边界值（最大长度、特殊字符）
  - 多余参数是否忽略

返回值验证：
  - 状态码正确（200/400/401/403/404/500）
  - 返回数据结构正确（字段名、类型）
  - 返回数据内容正确（与数据库一致）

业务逻辑：
  - 幂等性（同一请求重复提交 → 结果一致）
  - 顺序依赖（先调 A 再调 B，A 的结果影响 B）
  - 超时处理（接口响应超过 30s → 超时提示）

安全：
  - 鉴权（无 Token/过期 Token → 401）
  - 越权（A 用户请求 B 用户的数据 → 403）
  - 敏感数据加密（密码、手机号脱敏）
```

**场景 8：权限测试怎么测？**

```
菜单权限：
  - 不同角色登录 → 看到的菜单是否正确
  - 无权限菜单 → URL 直接访问是否被拦截

功能权限：
  - 无权限用户点击操作按钮 → 提示无权限
  - 低权限用户访问高权限 API → 403

数据权限：
  - 用户 A 只能看到自己的数据
  - 修改 URL 中的 ID → 不能访问他人数据（水平越权）
  - 普通用户访问管理员接口 → 被拦截（垂直越权）

常见越权手段（测试时尝试）：
  - 修改 URL 参数中的用户 ID/订单号
  - 修改请求体中的用户标识
  - 使用低权限 Token 访问高权限接口
```

**场景 9：兼容性测试怎么测？**

```
浏览器兼容：
  - 主流浏览器：Chrome / Firefox / Edge / Safari
  - 同一页面在不同浏览器的布局、样式、功能是否一致
  - JavaScript 在不同浏览器的兼容性

设备兼容：
  - PC / 手机 / 平板的响应式布局
  - 不同屏幕分辨率（1920x1080 / 1366x768 / 375x667）
  - 横屏/竖屏切换

系统兼容：
  - Windows / macOS / Linux
  - Android / iOS 不同版本
  - 浏览器不同版本（Chrome 120 vs Chrome 100）

网络兼容：
  - 4G / 5G / WiFi / 弱网环境
  - 网络切换（WiFi → 4G）时的状态保持
```

**场景 10：弱网/网络异常怎么测？**

```
弱网场景：
  - 页面加载超时 → 是否有 loading 提示
  - 请求超时 → 是否有重试机制
  - 图片/视频在弱网下是否降级加载

网络异常：
  - 断网时操作 → 是否有离线提示
  - 网络恢复后 → 数据是否自动刷新
  - 请求过程中断网 → 数据是否丢失

网络切换：
  - WiFi 切 4G → 页面是否刷新/报错
  - 4G 切 WiFi → 登录态是否保持

测试工具：
  - Chrome DevTools → Network → Slow 3G / Offline
  - Charles / Fiddler → 限速模拟
  - 真机测试（飞行模式切换）
```

### STAR 原则回答模板

面试中回答"请讲一个你最印象深刻的 Bug"或"介绍一下你的项目"时，用 **STAR 原则**组织回答：

| 要素 | 含义 | 话术示例 |
|------|------|---------|
| **S**ituation | 项目/场景背景 | "我在 XX 项目中负责订单模块的测试" |
| **T**ask | 你的任务 | "需要覆盖支付全流程，包括退款和异常场景" |
| **A**ction | 你做了什么 | "我用等价类+边界值设计了 50 个用例，发现了支付回调幂等性问题" |
| **R**esult | 结果/成效 | "提前发现了线上生产 Bug，避免了预计影响 10 万用户的故障" |

### 如何展示自动化项目经验

面试时展示自动化经验的核心策略：

1. **先讲项目背景** — 什么项目、团队规模、测试范围
2. **框架设计思路** — 为什么选择这个框架、解决了什么问题
3. **你的具体贡献** — 写了多少用例、覆盖多少接口、发现了什么 Bug
4. **技术细节** — 遇到什么技术难点、怎么解决的（如："框架不支持参数化，我引入了 DataProvider 改造了数据驱动层"）
5. **效果数据** — 自动化覆盖率、执行时间缩短了多少、线上漏测率变化

**"我不会直接说我会 Selenium，而是说：'我基于 Page Object 模式设计了一套自动化框架，覆盖了 300+ 用例，每次回归从 2 天缩短到 2 小时'"**

## 跨知识体系连接

### 与 [[AI应用开发知识体系]] 的连接

| 连接点 | 说明 |
|-------|------|
| **AI 辅助测试用例生成** | 用 LLM（Claude/GPT）基于需求文档自动生成测试用例，测试人员做 Review 和补充 |
| **AI 智能 Bug 分析** | 将日志/错误截图喂给 AI，自动识别错误原因、给出修复建议、分配合适的开发 |
| **视觉回归测试自动化** | 用 AI 做截图对比，解决传统像素对比误报率高的问题（如内容变化但功能正常） |
| **测试数据生成** | 用 AI 生成大量符合业务逻辑的测试数据，替代手工造数据的低效方式 |
| **测试报告智能总结** | 用 AI 将测试结果自动生成自然语言报告，减少人工汇总 |
| **知识库 RAG** | 将历史 Bug 和经验文档做成 RAG 知识库，新测试人员可以快速查询类似问题的处理方式 |

AI 应用开发能力不是替代测试，而是 **让测试人员从重复劳动中解放出来，聚焦在更有价值的探索性测试和测试设计上**。

### 与 [[Java开发知识体系]] 的连接

| 连接点 | 说明 |
|-------|------|
| **Java 是自动化框架的基础语言** | Selenium、Rest Assured、Appium、JMeter 脚本、TestNG/JUnit 全基于 Java |

| **集合与 Lambda** | 用例数据管理、列表筛选、Map 转换、Stream 操作无处不在 |

| **SQL** | 接口测试数据准备/清理、数据库断言、性能慢查询定位 |
| **Git** | 版本管理测试代码、CI 触发自动执行、多人协作 |

**不是你一边学测试一边丢了 Java，而是你用 Java 写出更好的测试框架。**

## 学习路径建议（结合路线图）

### 第 1 阶段：测试理论基础（路线图第1阶段，1-2周）
- 掌握质量模型、测试类型、测试级别
- 熟记 7 种测试设计方法
- 会写标准测试用例
- 理解 Bug 生命周期与测试流程

### 第 2 阶段：手工/功能测试实战（路线图第2阶段，2-3周）
- Web 功能测试：表单/链接/搜索/分页/权限测试
- APP 功能测试基础：安装卸载/中断/弱网/兼容性（了解即可）
- 接口测试基础：HTTP 协议、Postman、鉴权方式
- 在 Demo 项目上写 50+ 测试用例，提交 Bug，写测试报告

### 第 3 阶段：自动化测试（路线图第3阶段，4-6周）
- Java 基础（集合 + OOP + 异常 + IO/序列化）
- API 自动化（Rest Assured / requests + 数据驱动 + 框架设计）
- UI 自动化（Selenium + Page Object + 三种等待）
- 测试框架搭建（重试机制 + 日志 + 报告 + 并发执行）

### 第 4 阶段：CI/CD + Docker（路线图第3/6阶段，1-2周）
- Docker 基础：镜像/容器/Docker Compose 搭建测试环境
- CI/CD：Jenkins Pipeline / GitHub Actions 集成自动化测试
- Selenium Grid 分布式测试
- 测试环境管理最佳实践

### 第 5 阶段：性能测试（路线图第4阶段，2-3周）
- JMeter 完整流程（基准 → 负载 → 压力 → 稳定性）
- 性能指标（QPS/TPS/RT/P99）与分析
- 性能瓶颈定位（CPU/内存/IO/慢 SQL）

### 第 6 阶段：安全测试（路线图第5阶段，2-3周，差异化亮点）
- OWASP Top 10 核心漏洞理解
- SQL 注入 / XSS / CSRF 测试方法
- Burp Suite 抓包与安全测试
- 面试中作为差异化亮点展示

### 第 7 阶段：测试进阶（路线图第6阶段，持续提升）
- AI 辅助测试实践（AI 生成用例、Bug 分类、测试报告）
- 测试平台开发（Spring Boot + Vue）
- 测试质量度量与流程优化
- 持续学习：关注新技术和测试趋势
